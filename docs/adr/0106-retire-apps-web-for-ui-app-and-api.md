# ADR-0106: Retire `apps/web` in favor of `apps/ui-app` + a new `apps/api` backend

- **Status:** Accepted — 2026-10-31 (repository owner directed the retirement and the adapter-layer strategy in conversation; see decision log below).
- **Date:** 2026-10-31
- **Deciders:** repository owner
- **Related:** supersedes ADR-0096 (feature-owned web presentation and adapters), ADR-0100 (single-operator mode), ADR-0101 (remove the demo data path), ADR-0068-web-frontend-real-mode-data-boundary, ADR-0084 (real service adapter boundary) — all four stay historically accurate for the code they described, but no longer describe the canonical web stack. `interfaces/api/auth.py` (runtime token boundary) is unaffected and remains the hard constraint this decision is built around.

## Context

`apps/web` (`@raptix/web-raptix`) is the canonical web console as of the W16/W20 cutover: a React 19 + Vite frontend with its own nested backend at `apps/web/server` (`@raptix/web-raptix-server`, Fastify + Prisma), wired to the Python runtime's LangGraph HTTP API, to C2/sandbox/webshell integrations, and governed by roughly ten ADRs (0068, 0084, 0096, 0100, 0101, 0084...) plus the Makefile's `webraptix-*` target family and two compose files.

A second, independently developed frontend, `apps/ui-app`, was imported into the repo (checkpoint commit `1bd59088`). It is a standalone TypeScript/DOM/Vite application extracted from a different product ("CyberStrikeAI"), covering the same problem space — AI-assisted red-team operations: chat-driven agent tasks, projects, assets, vulnerabilities, C2, webshell, RBAC, skills, knowledge, HITL — but defined against its **own** API contract (`apps/ui-app/docs/openapi.yaml`, 300 operations across 229 paths; see `apps/ui-app/docs/api-contracts.md`). That contract's own documentation is explicit: *"The real Raptix backend is not available in this repository. Existing API interfaces are an export boundary, not a verified Raptix integration contract."* Its domain shape (`conversations`, `projects`, `vulnerabilities`, `assets`, `roles`, `rbac`, `wechat-robot`...) does not line up term-for-term with Raptix's actual domain model (OPPLAN/`EngagementContext`, the capability runtime, AKG, asset-map, governance, closure, scope, vault) that `apps/web`'s routes were built against.

The repository owner decided to make `apps/ui-app` the one canonical web frontend going forward and to retire `apps/web` (both the React frontend and its nested Fastify/Prisma server) immediately, rather than running the two in parallel during a gradual migration. The owner also decided that the gap between `apps/ui-app`'s existing contract and the real Raptix runtime is closed with a **backend-for-frontend (BFF) adapter layer** that translates Raptix's domain model into the shape `apps/ui-app` already expects, rather than rewriting `apps/ui-app`'s `src/api/`/`src/features/` to match the runtime's native shape. This keeps `apps/ui-app`'s large existing UI surface untouched and concentrates the translation risk in one new, explicit layer.

This is a hard constraint independent of this decision: `packages/raptix/raptix/interfaces/api/auth.py` states "Only the web API holds the runtime API token... so the runtime can never serve unauthenticated callers." A browser-side app can never hold `RAPTIX_RUNTIME_API_TOKEN_FILE`; some server-side process must sit between the browser and the LangGraph HTTP API. `apps/web/server` filled that role for `apps/web`; a new server must fill it for `apps/ui-app`.

## Decision

1. **`apps/ui-app` is the canonical web frontend.** `apps/web` (frontend and its nested `server/`) is deleted in this change. No parallel-run / strangler period — the owner accepted the resulting backend gap as a known, temporary state.
2. **A new package, `apps/api`, is the BFF/adapter backend for `apps/ui-app`.** Its target contract is `apps/ui-app/docs/openapi.yaml` / `api-contracts.md` as already written — `apps/ui-app`'s client code (`src/api/clients/*`, `src/platform/http.ts`, `src/platform/sse.ts`, `src/platform/ws.ts`) is not rewritten to match the runtime's native shape. `apps/api` is responsible for the translation in the other direction: Raptix domain → the contract `apps/ui-app` already speaks.
3. **`apps/api` holds the runtime token school.** It is the only process authorized to read `RAPTIX_RUNTIME_API_TOKEN_FILE` and call the LangGraph HTTP API (`/threads`, `/assistants`, `/runs`, plus the custom mounts in `interfaces/api/*`). `apps/ui-app` never receives that token.
4. **Infrastructure plumbing is salvaged, not rewritten.** `apps/web/server/src/integrations/{c2,sandboxes,webshell,environments,campaigns}` and `src/db/client.ts` talk to infrastructure (Docker/C2/sandbox/Prisma), not to `apps/web`'s UI contract; they are recovered from git history (pre-deletion commit) into `apps/api` rather than re-implemented from scratch.
5. **Routes without a Raptix-domain equivalent are stubbed, not silently dropped.** Where `apps/ui-app`'s contract has no corresponding Raptix concept (e.g. `wechat-robot`, parts of `builtin-tools`), `apps/api` returns an explicit "not implemented for this deployment" response rather than a fabricated success, and the gap is tracked in the implementation plan (`docs/design/2026-10-31-ui-app-integration-implementation-plan.md`) for an explicit accept/cut decision per route group.
6. **Build/CI/compose/launcher surfaces that referenced `apps/web` are updated in the same change set that deletes it**, not left dangling: `Makefile` (`webraptix-*` targets, and `quality`'s dependency on `webraptix-quality`), `docker-compose.web-raptix.yml`, `docker-compose.web-runtime.yml`, `infra/containers/web-raptix.Dockerfile`, and `apps/launcher/internal/sandboxes/*` references.

## Consequences

- **Easier:** `apps/ui-app`'s already-built UI surface (31+ feature modules, terminal/xterm, Cytoscape graph views, i18n, mobile-web) ships without a frontend rewrite. One frontend, one contract to keep stable.
- **Harder:** every one of `apps/ui-app`'s 300 documented operations needs a corresponding `apps/api` route before the matching feature works end to end; until then, those features run against nothing (not even a local mock — `apps/ui-app`'s demo/mock transport is explicitly non-canonical for this migration and is not a substitute for the real adapter). The translation layer (Raptix domain ↔ CyberStrikeAI-shaped contract) is a permanent piece of code to maintain, not a one-time migration script; a future Raptix domain change (e.g. a capability-runtime reshape) now has to be re-translated at this boundary too.
- **Given up:** `apps/web`'s existing, already-correct-to-the-domain routes, Prisma schema, and ~ten ADRs' worth of settled design (feature-owned adapters, real-mode-only data boundary, single-operator mode as applied there) stop describing anything live. They remain in `docs/adr/` as historical record of a design that is no longer in the tree.
- **Migration:** no strangler/parallel-run period. `apps/web` is deleted in the same PR as this ADR's acceptance. The implementation plan (see Related) tracks the route-by-route backfill of `apps/api` and is the live status document; this ADR does not restate that sequencing.

## Alternatives considered

- **Rewrite `apps/ui-app`'s API client layer to match the runtime's native domain shape (no BFF adapter).** Rejected by the owner: larger surface to change inside an already-large, newly-imported frontend; the BFF concentrates the one-time translation risk in a single new package instead of scattering it across `apps/ui-app/src/api/` and every feature's `service.ts`.
- **Keep `apps/web` running in parallel until `apps/api` reaches parity (strangler).** Rejected by the owner: explicit choice to retire `apps/web` immediately and accept a temporary backend gap for `apps/ui-app`, rather than carry two frontends/backends through the migration.
- **Delete `apps/web/server`'s infrastructure integrations along with the rest of `apps/web`.** Rejected: those modules (`c2`, `sandboxes`, `webshell`, `environments`, `campaigns`, the Prisma `db/client.ts`) are infrastructure plumbing independent of `apps/web`'s UI contract; re-implementing them from zero in `apps/api` would be pure, avoidable rework.
