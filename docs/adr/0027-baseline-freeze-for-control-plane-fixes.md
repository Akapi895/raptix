# 0027. Baseline freeze before control-plane fixes

- **Status:** Proposed
- **Date:** 2026-10-02
- **Deciders:** @PurpleCHOIms
- **Related:** [ARCHITECTURE_AUDIT.md](../../ARCHITECTURE_AUDIT.md), [ARCHITECTURE_AUDIT_FIX.md](../../ARCHITECTURE_AUDIT_FIX.md), [AGENTS.md](../../AGENTS.md), [docs/QUALITY_BAR.md](../QUALITY_BAR.md)

## Context

The architecture audit (`ARCHITECTURE_AUDIT.md`) identified 11 bottlenecks
across the agent control plane, with 5 marked P0/P1 for verification
priority. The follow-up review (`ARCHITECTURE_AUDIT_FIX.md`) reframed
those 5 as **5 break points in a single pipeline** rather than 5
independent bugs:

```
observed outcome → verified state transition → current operational state
→ planner decision → typed task → verified outcome
```

The review also proposed a **revised implementation order** that does
*not* follow the audit's P0-1 → P0-2 → P0-3 → P1-4 → P1-5 sequence.
The audit's priority column is "ưu tiên kiểm chứng" (verification
priority), not an optimal implementation order. The review's order is:

| Step | Fix | Semantics change |
|---|---|---|
| 0 | Freeze baseline | None (measurement only) |
| 1 | Typed failure/terminal outcome | Local (dispatch boundary) |
| 2 | KG freshness refresh | Local (lifecycle, no schema change) |
| 3 | IF contract consistency | Local (skill ACL, paths, tool slots) |
| 4 | Verified foothold gate | Decision boundary (IF→NP only) |
| 5 | Structured operational state | Decision boundary (shadow mode first) |

Steps 1–3 are local and low-risk; steps 4–5 change the decision
boundary and must be gated by regression evidence from steps 0–3.

**The problem:** we have no quantitative baseline against which to
measure whether each step actually improves things. The audit's
runtime evidence (A1: 204/224 repeated `ls` calls, 6 recursion errors,
4 `[TERMINAL]`, ~10M parent tokens) came from a benchmark
(`juice_shop_t2.py`) that does not exist in the current repo. The
current benchmark infrastructure is XBOW-based
(`benchmark/configs/decepticon-bench-v1.yaml`) with results under
`benchmark/results/<XBEN-ID>/<UTC>/report.json`.

Without a frozen baseline, every subsequent step risks the failure mode
flagged in the review: *"if an ablation reduces parent tokens but
shifts cost to workers, the current benchmark may mistake that for an
improvement"* (P2-10 measurement debt).

## Decision

We adopt a **baseline freeze** as Step 0 of the control-plane fix
sequence, before any code change. The freeze consists of:

1. **A metrics extraction script** (`scripts/baseline/extract_metrics.py`)
   that reads existing benchmark results and emits a structured
   baseline report covering:
   - `task()` dispatch count per run
   - redispatch count (same dispatch repeated)
   - calls without new information (repeated exact tool calls)
   - KG revision transitions (where trace data is available)
   - objective transitions (status changes)
   - invalid contract calls (skill-not-found, tool-not-in-slot)
   - IF→NP transition events
   - token usage (parent-only, with the caveat from P2-10)

2. **A fixture set** under `tests/fixtures/baseline/` with three
   categories, as specified in the review:
   - **Failed `task()` fixture**: a recorded dispatch that ended in
     recursion error or `[TERMINAL]`, extracted from an existing
     benchmark run or constructed synthetically if no real failure
     trace is available.
   - **KG fixture**: a synthetic node/edge update scenario that
     exercises the freshness lifecycle (revision X → write fact →
     next model turn), including the two regression cases the audit
     requires: edge-only mutation and same-second writes.
   - **Recon→exploit handoff fixture**: a handoff with observations
     but no confirmed sink, plus the five foothold states (A–E) from
     the audit's experiment 3:
     - A: one-shot RCE, no managed session
     - B: credential exists but unusable for desired access
     - C: live session, insufficient privilege
     - D: dead session
     - E: live access + required execution/reachability

3. **A baseline report** (`benchmark/baselines/<UTC>/baseline.json` +
   `baseline.md`) generated by running the extraction script against
   the existing `benchmark/results/` directory. This report is the
   regression fixture for steps 1–5.

4. **No code changes** in this step. The freeze is purely
   measurement infrastructure + fixtures + report.

## Consequences

- **Easier:** every subsequent step (1–5) has a quantitative
  before/after comparison. The review's regression principle
  (*"được phép làm chặt khi nào tuyên bố có usable foothold, nhưng
  không làm chặt exploit worker được phép suy luận hướng nào bên
  trong IF"*) becomes testable rather than aspirational.
- **Easier:** the fixture set is reusable across steps 1–5. Step 1
  uses the failed `task()` fixture; step 2 uses the KG fixture; step
  3 uses the recon→exploit handoff; step 4 uses foothold states A–E.
- **Harder:** the baseline is only as good as the data in
  `benchmark/results/`. If existing runs lack the trace detail needed
  for some metrics (e.g., KG revision transitions are not in
  `report.json`), those metrics will be marked `unavailable` in the
  baseline report rather than estimated. This is intentional — we
  prefer honest gaps over fabricated numbers.
- **Harder:** the baseline is a snapshot. If the benchmark
  infrastructure changes between step 0 and step 5, the baseline
  must be regenerated. The report includes a hash of the
  `benchmark/` directory at freeze time to detect drift.
- **Given up:** the ability to claim "improvement" without
  quantitative evidence. Every step 1–5 PR must include a
  before/after diff against this baseline.
- **Migration:** none. No production code changes.

## Alternatives considered

- **Skip baseline, start with step 1 directly.** Rejected because the
  review explicitly warns that P2-10 measurement debt means
  parent-only token reductions can mask worker cost shifts. Without a
  baseline, we cannot distinguish real improvement from measurement
  artifact.
- **Re-run the old `juice_shop_t2` benchmark to regenerate A1/B1
  evidence.** Rejected because `juice_shop_t2.py` does not exist in
  the current repo, and the audit itself notes A1/B1 are not a valid
  A/B comparison (different image, prompt, RoE, ground-truth
  denominator). Reconstructing them would be busywork that doesn't
  improve the baseline.
- **Use LangSmith traces as baseline.** Rejected because LangSmith
  traces are not committed to the repo and are not reproducible
  across environments. The baseline must be derivable from
  artifacts in the repo.
- **Defer baseline to after step 1.** Rejected because step 1
  changes the dispatch boundary, which would contaminate any
  baseline measured after it. The baseline must be pre-change.
