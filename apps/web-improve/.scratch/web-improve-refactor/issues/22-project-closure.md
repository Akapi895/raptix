# 22: Closure policy and independent confirmation

**What to build:** Move closure checklist and request/confirm/reopen governance to real domain/handlers, including policy exceptions already exposed by the export.
**Blocked by:** 21.
**Status:** resolved
**Owner:** Closure domain/actions.
**Contract:** [execution.md](../execution.md).

- [x] Checklist evaluates operations, live sessions, findings, delivery and approvals at request and confirmation, not just on page render.
- [x] Documented no-findings waiver/agent reservation behavior is characterized and retained explicitly rather than silently dropped.
- [x] Independent authorized confirmation is required; a late blocking change prevents closure; reopening requires role/reason and audit.
- [x] Tests exercise real closure actions with each failed condition and valid completion; legacy/new close panels agree.

## Implementation

Feature-local handlers (ADR-0067 pattern, ticket 21 exemplar):

- `src/features/closure/service.ts` — closure governance owned by the handler:
  - `evaluateCloseChecklist(db, pid, { waiverNoFindings? })` — the canonical five-condition checklist (c1 operations, c1b live sessions, c2 findings, c3 delivered report, c4 outstanding approvals) derived from canonical state on every call and never persisted (no facet writes; one derivation for the store export, the close panel and both handlers). The documented no-findings waiver flips c3 only when requested and no confirmed finding exists.
  - `closePanelItems` — the close console's display list: the checklist plus the c5 agent-reservation row (moved verbatim from the panel), so the panel can never drift from the policy.
  - `requestCloseTransaction` — manager-gated (`requestClose`), deliberately NOT checklist-gated: the request is a UI-only request for independent review and is accepted with failing conditions. The evaluation is recorded at request time (note names open conditions, itemized diff, `refId: 'no-findings-waiver'` marker); both audit rows (`Requested project closure` + `Closure reason …`) and the reviewer notice commit in the one atomic commit. Refusals: `not-found` → `forbidden` → duplicate pending `conflict` → missing reason `validation`.
  - `confirmCloseTransaction` — the gated resolve (G-5 closed): `not-found` → non-close/not-pending `conflict` → `confirmClose` role `forbidden` → requester self-confirm `forbidden` (four-eyes, identity-based) → checklist RE-DERIVED from canonical state at confirmation `validation` naming each blocker — so a late blocking change (resumed operation, new live session, undispositioned finding, confirmed finding voiding the waiver) prevents closure. Decision + closed read-only state + audit commit together.
  - `reopenProjectTransaction` — admin role and a required, audited reason enforced by the handler (the UI used to gate these alone): `not-found` → not-closed `conflict` → `forbidden` → missing reason `validation`.
- `src/features/estop/service.ts` — the emergency-stop console's transitions as typed transactions. Invariant enforced at the handler: a stop is ALWAYS an action with an immediate visible response, never a passive status — `requestEmergencyStopTransaction` commits the requested stop state, the Pending audit row and the workspace notice in ONE immediate commit before any simulated acknowledgement delay, returns the affected operations, and refuses a missing reason (`validation`) or a role without `estop` (`forbidden`). `acknowledge` (ops → estop with steps Unknown/not-run, sessions → revoking, audit) and `finalize` (sessions terminated, agents released, stopped) each commit atomically; `fail`/`unknown` record explicit uncertainty; `resolveStop` keeps the documented baseline manual-confirm behavior whose hardening is ledger G-10 (ticket 28).
- Store wiring: `A.requestClose`/`A.confirmClose`/`A.reopen` return `Res` and delegate to the handlers; `A.emergencyStop`/`A.retryStop`/`A.resolveStop` delegate every transition to the estop handlers, keeping only the demo's simulated outcome switch and tracked delays (disposed on reset). `closureChecklist` re-exports the feature derivation (same five conditions; completion % unchanged). `decideApprovalTransaction` no longer approves closure requests — they resolve only through the gated confirmation (bypass closed); returned decisions still flip `review → active`. The close console (`CloseTab`) renders the shared derivation and surfaces handler refusals from the modal submit, Approve Closure and the TeamTab decision; `useReopen` surfaces the reopen refusal.
